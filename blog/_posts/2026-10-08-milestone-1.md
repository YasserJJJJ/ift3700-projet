Ce jalon couvre l'acquisition, un explorateur interactif, les données ordonnées et les visualisations du volet **IFT3700**.

## 1. Acquisition des données

Pour obtenir les données, nous avons créé la classe `NHLClient`, dans le module
`ift3700/acquisition.py`. Elle permet de télécharger les événements play-by-play
d'un match et de les sauvegarder en JSON. Lors d'un nouvel appel, elle charge le
fichier local plutôt que d'effectuer une nouvelle requête. Ce cache permet de
reprendre une acquisition interrompue et de limiter les appels à l'API publique.

### Identifier les matchs et les saisons

Nous utilisons le point d'accès suivant :

```text
https://api-web.nhle.com/v1/gamecenter/{game_id}/play-by-play
```

Un identifiant de match comporte dix chiffres, selon la structure `YYYYTTNNNN`.
Par exemple, `2017020001` désigne un match de la saison **2017-18** : `2017` est
l'année de début de saison et `02` indique un match de saison régulière. Le code
`03` correspond aux séries éliminatoires. Les quatre derniers chiffres identifient
le match au sein de la saison et du type ; les IDs des séries ne forment pas une
suite continue.

Pour obtenir la liste des matchs, `list_games()` interroge le catalogue paginé de
l'API des statistiques de la LNH. Nous conservons les types `02` et `03`, ainsi que
les matchs terminés, identifiés par `gameStateId=7` dans ce catalogue. Les matchs
de séries prévus mais non joués ne sont donc pas considérés comme des fichiers
manquants.

### Télécharger un match et réutiliser le cache

Depuis la racine du projet, après l'installation décrite dans le README :

```python
from ift3700 import NHLClient

client = NHLClient(data_dir="data/raw")
game = client.get_game(2017020001)
print(game["id"], len(game["plays"]), "événements")

# Le deuxième appel doit charger le fichier local.
requests_before = client.request_count
same_game = client.get_game(2017020001)
assert client.request_count == requests_before
assert same_game == game
```

Si le match n'est pas déjà présent, le premier appel le télécharge. Sinon, il
utilise immédiatement le cache. Pour cet exemple, le fichier se trouve dans
`data/raw/20172018/regular/2017020001.json` ; les matchs de séries sont rangés dans
un dossier `playoffs` distinct.

Voici la méthode centrale de la classe. Cet extrait utilise les fonctions de
validation et de lecture/écriture du module ; le code complet est fourni avec
le projet dans `ift3700/acquisition.py`.

```python
def get_game(self, game_id: int, *, force: bool = False) -> dict:
    """Charger le JSON local, ou télécharger/valider/sauvegarder le match."""
    path = self.game_path(game_id)
    if path.exists() and not force:
        value = self._validate_game(_read_json(path), game_id)
        self.cache_hits += 1
        return value
    if self.offline:
        raise AcquisitionError(f"Match absent du cache : {path}")
    url = f"https://api-web.nhle.com/v1/gamecenter/{game_id}/play-by-play"
    value = self._validate_game(self._get_json(url), game_id)
    _write_json(path, value)
    return value
```

Le client vérifie notamment l'identifiant, la saison, le type et les événements
du match avant de sauvegarder ou de retourner les données. Les erreurs temporaires
font l'objet de nouvelles tentatives, avec un délai entre les requêtes. L'écriture
par remplacement atomique évite de laisser un fichier final partiellement écrit.

### Acquérir les huit saisons demandées

```python
for year in range(2016, 2024):
    report = client.download_season(year)
    if not report["complete"]:
        raise RuntimeError(
            f"Acquisition incomplète pour {year} : {report['failed']}"
        )
```

Les années **2016 à 2023** désignent les saisons **2016-17 à 2023-24**, inclusivement.
Par défaut, `download_season()` récupère la saison régulière et les séries. Son
rapport distingue les matchs téléchargés, ceux déjà présents et les échecs.
Une relance recharge les fichiers valides et tente de récupérer les matchs
encore absents.

Chaque membre peut choisir son emplacement de stockage avec `data_dir` ou, lorsque
cet argument est omis, avec la variable d'environnement `NHL_DATA_DIR` :

```bash
export NHL_DATA_DIR="/chemin/vers/mes-donnees-LNH"
```

Dans ce cas, on crée le client avec `NHLClient()`. Sans argument ni variable, le
chemin par défaut est `data/raw`. Les données brutes restent sur le disque local
et sont exclues du dépôt Git par `.gitignore`.

## 2. Outil de débogage interactif

L'outil permet de choisir la saison, le type de match, le match et l'événement.
Il dessine les coordonnées brutes sur la patinoire fournie et montre le JSON de
l'événement, y compris lorsque ses coordonnées sont absentes.

```python
from IPython.display import display
from ift3700.explorer import build_explorer
display(build_explorer("data/raw", offline=True))
```

Code de l'outil :

```python
"""Explorateur des événements bruts avec ipywidgets et matplotlib."""

from __future__ import annotations

import html
import json
from pathlib import Path

import matplotlib.pyplot as plt
import numpy as np

from .acquisition import AcquisitionError, NHLClient, season_id

RINK = Path(__file__).resolve().parents[1] / "figures" / "nhl_rink.png"

def draw_event(game: dict, index: int):
    """Dessiner les coordonnées brutes ; ne pas changer les côtés du match."""
    event = game["plays"][index]
    details = event.get("details", {})
    figure, axis = plt.subplots(figsize=(11, 5))
    axis.imshow(plt.imread(RINK), extent=(-100, 100, -42.5, 42.5), origin="upper")
    x, y = details.get("xCoord"), details.get("yCoord")
    if isinstance(x, (int, float)) and isinstance(y, (int, float)) and np.isfinite([x, y]).all():
        axis.scatter([x], [y], s=180, color="#162f89", edgecolors="white", linewidths=2, zorder=3)
        axis.annotate(f"({x}, {y})", (x, y), xytext=(8, 10), textcoords="offset points")
    else:
        axis.text(0, 0, "Cet événement ne contient pas de coordonnées.",
                  ha="center", bbox={"facecolor": "white", "alpha": 0.9})
    period = event.get("periodDescriptor", {}).get("number", "?")
    axis.set_title(f"Match {game['id']} · {event.get('typeDescKey', '?')} · "
                   f"P{period} {event.get('timeInPeriod', '?')} · événement {event.get('eventId', '?')}")
    axis.set(xlim=(-100, 100), ylim=(-42.5, 42.5), xlabel="x (pieds)", ylabel="y (pieds)")
    axis.set_aspect("equal")
    figure.tight_layout()
    return figure

def build_explorer(data_dir=None, *, offline=True):
    """Retourner un widget : saison -> type -> match -> tous ses événements."""
    import ipywidgets as widgets
    from IPython.display import HTML, display

    client = NHLClient(data_dir, offline=offline)
    season = widgets.Dropdown(options=[(f"{y}-{str(y+1)[2:]}", y) for y in range(2016, 2024)], description="Saison :")
    kind = widgets.Dropdown(options=[("Saison régulière", 2), ("Séries", 3)], description="Type :")
    game = widgets.Dropdown(options=[], description="Match :", layout=widgets.Layout(width="420px"))
    event = widgets.IntSlider(value=0, min=0, max=0, description="Événement :", continuous_update=False,
                              layout=widgets.Layout(width="700px"))
    previous = widgets.Button(description="← Précédent")
    following = widgets.Button(description="Suivant →")
    status = widgets.HTML()
    output = widgets.Output()
    state = {"game": None, "updating": False}

    def render(change=None):
        if state["updating"] or state["game"] is None:
            return
        data = state["game"]
        selected = data["plays"][event.value]
        with output:
            output.clear_output(wait=True)
            figure = draw_event(data, event.value)
            display(figure)
            plt.close(figure)
            display(HTML("<pre style='max-height:350px;overflow:auto'>" +
                         html.escape(json.dumps(selected, ensure_ascii=False, indent=2)) + "</pre>"))

    def load_game(change=None):
        if state["updating"] or game.value is None:
            return
        state["updating"] = True
        state["game"] = None
        try:
            data = client.get_game(game.value)
            state["game"] = data
            event.value = 0
            event.max = len(data["plays"]) - 1
            away = data.get("awayTeam", {}).get("abbrev", "Visiteurs")
            home = data.get("homeTeam", {}).get("abbrev", "Domicile")
            status.value = html.escape(f"{away} chez {home} · {data.get('gameDate', '')} · {len(data['plays'])} événements")
        except AcquisitionError as error:
            status.value = html.escape(str(error))
            output.clear_output()
        finally:
            state["updating"] = False
        render()

    def load_options(change=None):
        state["updating"] = True
        state["game"] = None
        try:
            identifiers = client.list_games(season.value, game_types=(kind.value,))
            game.options = [(str(identifier), identifier) for identifier in identifiers]
            if identifiers:
                game.value = identifiers[0]
            if not identifiers:
                status.value = "Aucun match pour cette sélection."
                output.clear_output()
        except AcquisitionError as error:
            game.options = []
            status.value = html.escape(str(error))
            output.clear_output()
        finally:
            state["updating"] = False
        load_game()

    season.observe(load_options, names="value")
    kind.observe(load_options, names="value")
    game.observe(load_game, names="value")
    event.observe(render, names="value")
    previous.on_click(lambda button: setattr(event, "value", max(event.min, event.value - 1)))
    following.on_click(lambda button: setattr(event, "value", min(event.max, event.value + 1)))
    load_options()
    return widgets.VBox([widgets.HBox([season, kind]), game, status, event,
                         widgets.HBox([previous, following]), output])
```

## 3. Données ordonnées

Une ligne correspond à un tir cadré (`shot-on-goal`) ou un but (`goal`), avec une
clé unique `(game_id, event_id)`. Les tirs manqués et bloqués sont exclus. Les noms
des joueurs sont joints aux identifiants via `rosterSpots` ; une information
absente reste manquante. Il n'y a pas de suppression globale des événements
incomplets : chaque analyse ne retire que les lignes dont elle a besoin.

Les colonnes `x` et `y` conservent les coordonnées originales. Les coordonnées
normalisées placent le filet attaqué à droite. Le côté du domicile est pris dans
`homeTeamDefendingSide` pour chaque événement. Certains JSON changent de repère
au milieu d'une période déclarée : nous utilisons alors le côté de l'événement
et signalons le conflit dans la provenance. Ce champ de l'API peut toutefois être
inversé pour une période entière : c'est le cas dans sept périodes de trois matchs
(`2019020249`, `2019020256` et `2020020175`), où toutes les zones `O`/`D` le
contredisent. Lorsqu'au moins cinq zones contredisent ainsi, sans exception, le côté
de la période, la zone prime (**152 événements**, provenance
`zone_code_overrides_api_side`). Pour tous les événements, un contrôle final rend la
direction et la distance manquantes si la zone déclarée contredit la position
normalisée ; les coordonnées brutes sont conservées. Si ce champ manque, un côté de
période cohérent est utilisable. Sinon, les zones `O` et `D`
des tirs/buts indiquent le côté attaqué : un tir en zone offensive se trouve
du côté du filet adverse, et un tir en zone défensive du côté du filet de
l'équipe qui tire. Nous retenons les votes unanimes d'une période ; une majorité
d'au moins 90 % est également utilisable si au moins trois votes existent,
mais elle est marquée comme inférée. Un événement contredisant cette majorité
conserve une direction inconnue. En dernier recours, seulement en l'absence
de tout vote de zone, une autre inférence exige au moins trois tirs cadrés/buts dans la période et
une médiane des abscisses, ajustées selon l'équipe, éloignée d'au moins 25 pieds
du centre. Sinon, la direction et la distance restent inconnues. Une rotation
de 180° change le signe de **x et y**. Les tirs de fusillade restent dans le
tableau mais sont exclus des analyses agrégées. Les sources de direction et
les cas de métadonnées contradictoires sont conservés dans `direction_source`
et décomptés à la fin de l'article.

### 3.1. Force sur la glace : catégorie et force réelle

**Dérivation à partir du `situationCode`.** Chaque tir et chaque but porte un
code à quatre chiffres `[gardien visiteur][patineurs visiteurs][patineurs locaux][gardien local]`.
Nous le lisons du point de vue de l'équipe qui tire : si elle joue à domicile,
ses patineurs sont le troisième chiffre et ceux de l'adversaire le deuxième ;
si elle est en visite, c'est l'inverse. Par exemple, `1451` donne **5 contre 4**
pour l'équipe locale et **4 contre 5** pour l'équipe visiteuse.

- La **force réelle** (`strength_detail`) est ce couple de patineurs, écrit `5c4`,
  `4c4`, `6c5`, etc. Les nombres eux-mêmes restent dans `own_skaters` et
  `opponent_skaters`.
- La **catégorie** (`strength`) n'est calculée que si **les deux gardiens sont dans
  leur filet** : autant de patineurs de chaque côté donne `EV` (forces égales),
  davantage pour l'équipe qui tire donne `PP` (avantage numérique) et moins donne
  `SH` (désavantage numérique). Un champ explicite EV/PP/SH aurait priorité, mais
  l'API actuelle n'en fournit pas.

La même règle s'applique aux tirs et aux buts. Hors fusillades, la catégorie est
connue pour **97,5 %** des 646 116 tirs cadrés et buts : 476 559 tirs et 43 224 buts
à forces égales, 79 101 tirs et 12 259 buts en avantage numérique, 16 925 tirs
et 1 620 buts en désavantage numérique. La situation `5c5` représente 78 % des
événements, et `5c4` 13,5 %.

**Cas limites que le code ne règle pas directement.**

- **Gardien retiré** (`0651`, `1560`, environ 13 900 événements) : un `6c5`
  peut correspondre à un attaquant supplémentaire à forces égales en fin de match
  ou à un avantage numérique avec le gardien retiré. Comparer les patineurs
  confondrait ces cas, donc la catégorie reste **manquante**, alors que
  `strength_detail` et `empty_net` restent renseignés.
- **Pénalité différée** : l'équipe qui va bénéficier de la pénalité retire son
  gardien avant que le jeu soit arrêté. Le code montre alors un `6c5` alors
  qu'aucun avantage numérique n'a encore commencé. C'est le même code qu'un retrait
  de fin de match. L'API inscrit toutefois un événement `delayed-penalty` au début
  de la séquence, qui permettrait de distinguer ces cas ; nous ne l'exploitons pas
  encore et la catégorie reste manquante.
- **Tirs de pénalité** (`1010`, 171 événements hors fusillade) : un tireur seul
  face au gardien, sans force de jeu au sens habituel ; la catégorie reste manquante.
- **Pénalités coïncidentes et prolongation** : `4c4` et `3c3` sont bien des forces
  égales (`EV`), mais leur contexte diffère d'un `5c5`, d'où l'intérêt de garder
  la force réelle à côté de la catégorie.
- **Instantané** : le code décrit les joueurs sur la glace au moment de l'événement.
  Il ne dit pas combien de temps il reste à une pénalité, ni si un but en avantage
  numérique y met fin.

**Vérifier ou reconstruire la force sans `situationCode`.** On parcourrait **tous**
les événements dans l'ordre chronologique en maintenant la liste des pénalités
actives avec leurs durées (`penalty`, champ `duration`). Il faut alors gérer les
pénalités coïncidentes, les doubles mineures, les majeures, la fin d'une mineure
après un but en avantage, les changements de période et les règles de
prolongation. Les retraits de gardien ajoutent une difficulté, car ils
n'apparaissent pas comme des événements. La même reconstruction servirait de
**contrôle** du code : un `5c4` qui ne correspond à aucune pénalité active serait
suspect. On pourrait aussi comparer nos buts `PP` et `SH` par équipe aux totaux
officiels de l'API des statistiques. Cette reconstruction n'est pas implémentée
pour ce jalon.

### 3.2. Caractéristiques supplémentaires possibles

- **Distance au filet** : après normalisation du sens d'attaque, mesurer la
  distance euclidienne au but situé en `(89, 0)` pieds. Cette caractéristique
  est déjà utilisée pour les figures ; sans coordonnées ou direction fiable,
  elle reste manquante.
- **Angle du tir** : calculer l'angle par rapport à l'axe du filet à partir des
  coordonnées normalisées, en traitant explicitement les tirs derrière la ligne
  de but. Il pourrait distinguer deux tirs aussi proches mais différemment orientés.
- **Rebond potentiel** : repérer un second tir de la même équipe quelques secondes
  après un premier tir cadré, dans la même période, sans interruption entre les
  deux. La fenêtre temporelle doit être déclarée et validée ; ce serait un proxy,
  car le jeu décrit ne prouve pas toujours qu'il s'agit d'un rebond.
- **Contre-attaque potentielle** : repérer une récupération ou une séquence allant
  rapidement de la zone défensive vers un tir offensif. Les événements sont
  espacés et la possession n'est pas observée en continu, donc il faudrait
  présenter cette variable comme un indicateur approximatif.

## 5. Cartes de tirs offensives interactives

### 5.1. Méthode et interprétation

Nous construisons les cartes avec des histogrammes NumPy et des graphiques
Plotly standards, sans bibliothèque spécialisée de visualisation de hockey.
Les tirs cadrés, buts inclus, sont orientés vers le filet de droite, puis
regroupés en cases de **5 × 5 pieds** dans la zone offensive
(`25 ≤ x ≤ 100`). Aucun lissage n'est appliqué.

L'image de la patinoire couvre les coordonnées physiques
`[-100, 100] × [-42.5, 42.5]`. Pour une image de largeur W et de hauteur H,
la correspondance avec les pixels est `(x+100)/200 × (W-1)` horizontalement
et `(42.5-y)/85 × (H-1)` verticalement. Elle permet de superposer les tirs
à la patinoire en respectant son orientation et ses dimensions.

Pour chaque case spatiale b et chaque saison, nous calculons :

```text
taux_ligue(b)  = nombre_tirs_ligue(b) / (2 × nombre_matchs_ligue)
taux_équipe(b) = nombre_tirs_équipe(b) / nombre_matchs_équipe
excès(b)       = taux_équipe(b) - taux_ligue(b)
```

Le facteur deux dans le taux de la ligue tient compte des deux équipes présentes
dans chaque match. Tous les matchs terminés de saison régulière contribuent
aux dénominateurs, même lorsque certains tirs n'ont pas de coordonnées
exploitables. Les événements de fusillade sont exclus ; les tirs en filet désert
restent inclus. Avec l'hypothèse simplifiée de 60 minutes par match, l'unité est
le **nombre de tirs par heure-équipe**. Les minutes supplémentaires de
prolongation ne sont pas ajoutées à cette exposition.

Une case **rouge** indique que l'équipe tire davantage que la moyenne de la ligue
à cet endroit ; une case **bleue** indique qu'elle y tire moins. Une couleur proche
du blanc indique un écart faible. Il s'agit d'une différence de fréquence,
et non d'un pourcentage de conversion ou d'une estimation des buts attendus.
Une case bleue peut donc contenir beaucoup de tirs si la moyenne de la ligue
y est encore plus élevée. L'échelle de couleurs, centrée sur zéro, est la même
pour les cinq saisons afin de permettre leur comparaison.

Pour interpréter les cartes, nous examinons notamment la zone centrale devant
le filet, les côtés et les régions plus éloignées, vers la ligne bleue.
Un excès près du but signale davantage de tirs depuis cette région, mais
ne prouve pas que chacun constitue une meilleure occasion. Les cartes
décrivent aussi la répartition spatiale : une équipe peut présenter un excès
dans une partie de la zone centrale et un déficit juste devant le filet.

Sur l'ensemble des **39 270 cases** (équipes × saisons × cases), les écarts restent
modestes : environ **95 %** des cases (94,6 %) s'écartent de la moyenne de la ligue
de moins de **0,1 tir par heure-équipe**, et environ **99 %** (99,2 %) de moins de
**0,2**. Nous comparons ensuite l'écart **absolu** moyen par case dans trois régions
définies sur les bords des cases : devant le filet (`70 ≤ x < 90`, `|y| < 17.5`,
le rectangle de la section 5.2), près de la ligne bleue (`25 ≤ x < 45`, toute la
largeur) et dans les coins (`x ≥ 75`, `|y| ≥ 27.5`). Il vaut **0,071** devant le
filet, **0,030** près de la ligne bleue et **0,011** dans les coins, soit des rapports
d'environ **2,3** et **6,5**. Les cartes des équipes diffèrent donc surtout devant
le filet. Cette mesure mélange toutefois excès et déficits, et les régions où l'on
tire beaucoup ont naturellement de plus grands écarts bruts : elle décrit où les
cartes varient, pas directement la qualité d'une attaque. Avec des cases de 5 pieds
et sans lissage, une case isolée très colorée peut aussi refléter le hasard ; nous
accordons plus de poids aux zones où plusieurs cases voisines vont dans le même sens.

la défense et les performances des gardiens peuvent aussi intervenir.

### 5.3. Buffalo et Tampa Bay, de 2018-19 à 2020-21

En **2018-19**, Buffalo produit légèrement plus de tirs cadrés dans la zone
offensive que Tampa Bay : **30,93 contre 30,55 par heure-équipe**.
Les deux équipes dépassent la moyenne de la ligue, mais leurs répartitions
spatiales diffèrent. Tampa Bay présente un excès marqué dans une partie
centrale de l'enclave, un peu en retrait du filet, et un déficit dans certaines
cases immédiatement devant le but. Buffalo montre une répartition plus diffuse,
avec également un déficit proche du filet. Dans le rectangle central défini
en section 5.2, Tampa Bay totalise **9,34 tirs par heure-équipe**, contre
**8,88 pour Buffalo**. L'écart de volume total masque donc une différence
dans les endroits d'où proviennent les tirs.

En **2019-20**, Buffalo est nettement sous la moyenne de la ligue dans l'ensemble
de la zone offensive (**−1,90**), tandis que Tampa Bay s'y situe presque exactement
(**−0,04**). Tampa Bay conserve un volume supérieur :
**29,69 tirs par heure-équipe**, contre **27,83 pour Buffalo**. Sa carte montre
des excès dans plusieurs cases centrales, tout en conservant un déficit
immédiatement devant le filet ; celle de Buffalo présente des déficits
dans plusieurs régions centrales. Dans notre rectangle proche du but,
les volumes sont néanmoins très voisins : **8,76 pour Tampa Bay** et
**8,46 pour Buffalo**. La présence de quelques cases rouges ne signifie donc
pas nécessairement un avantage important dans toute cette région.

En **2020-21**, l'écart devient plus net : Tampa Bay produit **29,07 tirs
par heure-équipe** dans la zone offensive, contre **27,09 pour Buffalo**.
Tampa Bay dépasse légèrement la moyenne de la ligue, tandis que Buffalo reste
en dessous. Dans le rectangle proche du filet, Tampa Bay obtient
**9,96 tirs par heure-équipe**, contre **8,48 pour Buffalo**, soit un écart
de **1,48**. La carte de Buffalo conserve un déficit visible devant le but,
tandis que celle de Tampa Bay montre davantage d'excès dans certaines parties
de la zone centrale. Sur cette saison, les données indiquent donc un avantage
de Tampa Bay à la fois dans le volume offensif total et dans cette région proche
du filet.
